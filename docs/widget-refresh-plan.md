# Widget refresh: audit and improvement plan

Audit of every path by which kofin makes home-screen widgets and skin containers re-read the library, why the current shape over-refreshes (visible flicker, focus churn, no-op scans, a vacuum per refresh), and a plan to port pvr.kofin's fingerprint gate so the UI only moves when what it renders actually changed.

Companion precedent: pvr.kofin polls the server on a cadence and used to fire `TriggerTimerUpdate`/`TriggerRecordingUpdate` every pass, flickering the Live TV widgets even when nothing changed; it now fingerprints the fields Kodi renders and refreshes only the halves whose fingerprint moved (`src/iptvsimple/jellyfin/JellyfinRecordingManager.h` `ReloadChange`, `.cpp` `ComputeFingerprints`, consumed in `IptvSimple.cpp`'s poll loop). This plan is the plugin.video.kofin translation of that idea, adjusted for the fact that our "poll" is already change-driven — here the no-op class is echoes and bookkeeping cycles, not empty polls.

## How a refresh actually reaches the screen

Kofin writes Kodi's SQLite files directly, which raises no library event, so nothing on screen moves until kofin fires a builtin (`sync/library.py refresh_libraries`). What each builtin does on the Kodi side determines what "a refresh" costs:

- Home widgets are containers with a `<content>` path (contuary: `videodb://`, `musicdb://`, `library://`, skin `.xsp` — all native, no plugin widget paths), each backed by a `CDirectoryProvider` (`xbmc/guilib/listproviders/DirectoryProvider.cpp`, verified on Omega).
- `CDirectoryProvider::Announce` invalidates on VideoLibrary/AudioLibrary messages `OnScanFinished`, `OnCleanFinished`, `OnUpdate`, `OnRemove`, `OnRefresh` — but only for providers whose *fetched items* include the matching media kind (`m_itemTypes` guard). A video refresh therefore never re-fetches music widgets and vice versa; kofin's video/music split is already the finest granularity Kodi offers.
- `UpdateLibrary(video)` runs a no-op scan (every kofin path row carries `noUpdate=1`), whose OnScanFinished both resets the cached `Library.HasContent` bools and invalidates every non-empty video widget. `UpdateLibrary(music,<nonexistent probe>)` is the music equivalent (see `_refresh_music` for why a real music scan is unusable). Each refresh also costs the post-scan "Compressing database" vacuum observed live.
- An invalidated provider re-fetches its directory and swaps its item list wholesale — `OnJobComplete` does no same-content comparison — so every invalidation re-renders the widget even when the rows came back identical. Gating at the source is the only flicker fix; nothing downstream de-duplicates.
- A provider whose last fetch returned zero items has an empty `m_itemTypes`, so it is *deaf* to library announcements: a widget built against an empty library can never be woken by any scan event. Together with the skin's `condition="Library.HasContent(...)"` include gates (evaluated at window load), this is why the empty→populated transition genuinely requires `ReloadSkin()` and cannot be replaced by more scanning. The current design is right; only its timing is fragile (F6).
- Kodi also invalidates widgets *natively*, without kofin's involvement: `Player.OnPlay`/`OnResume`/`OnStop` invalidate every provider sorted `SortByNone`, `SortByLastPlayed`, `SortByPlaycount` or `SortByLastUsed` (and the Player flag bypasses the item-type guard), and Kodi's own MyVideos/MyMusic writes after library-linked playback (bookmark, playcount) announce `OnUpdate`. Most contuary widget includes pass no `sortby`, so they are `SortByNone` and re-fetch on every play/stop of anything.

## Refresh inventory (today)

- End of a drained sync cycle: `service()` → `refresh_libraries(touched_databases)` (`sync/library.py:571`).
- Mid-cycle, additions written while a metadata backlog remains: `refresh_added()` → `refresh_libraries(added_databases)` (`:976`) — this is the "new content visible before the backlog drains" path, and it is working as designed (log: `--[ new content visible: video ]` seconds after a FastSync).
- After *every* processed command, unconditionally: `process_commands` tail → `refresh_libraries(touched_databases or {"video"})` (`:643`).
- End of every FullSync pass, including update-mode passes that only *plan*: `FullSync.start` → `refresh_libraries` over the synced classes (`sync/full_sync.py:297-308`).
- Database migrations at startup: `check_version` → `UpdateLibrary(video)` + `ReloadSkin()` (`:410`).
- First video content: `_video_content_hidden` → `UpdateLibrary(video)`, wait 2 s, `ReloadSkin()` (`:877-890`).
- Any refresh while a media window is up: `Container.Refresh` on whatever the user is looking at (`:895`).
- Plugin process: `Container.Refresh` after watched/favorite/delete actions (`plugin/actions.py:26`) and after a Who's-watching change (`plugin/adduser.py:226`) — listing-only, fine.

## Findings

F1 — the `process_commands` tail refresh (`library.py:641-643`) is spurious or misdirected for most commands. It fires after FastSync (queued work only — the drain refreshes later), after SyncMusicPlaylists/CleanupMusicPlaylists (file writes, no DB rows), and after real syncs whose FullSync already refreshed at `start()`'s end. Worse, its `or {"video"}` fallback aims at the wrong database: at tail time `touched_databases` is still empty (workers start on *later* ticks), so a music-only command refreshes video widgets. Every screensaver wake and websocket reconnect enqueues FastSync (`service/main.py:450,410`), so today every wake/reconnect costs one `UpdateLibrary(video)` with nothing to show.

F2 — update-mode FullSync refreshes at plan time. `FullSync.start` refreshes unconditionally before the `update_library` branch, but update mode has only *planned* work and written nothing; the drain that writes it refreshes again. Live proof in kodi.log 2026-08-03: each per-library `UpdateLibrary` command at 15:39:15 / 15:40:23 produced *two* music probe scans (15:39:21+15:39:33, 15:40:30+15:40:41) — plan-time and drain-time — plus the F1 tail's video refresh, so one logical update = three widget invalidations.

F3 — our own playback reporting comes back as work. Every stop/seek the player reports (`service/player.py`) is echoed by the server as `UserDataChanged` (with a second `UnplayedItemCount` entry for the parent folder), and each echo becomes a one-item userdata cycle ending in a refresh (log 15:48:06→15:48:08, 15:49:52, 17:54:16, 17:54:46: echo → `q:userdata/Movie` → drain). A music playlist track change produces *two* echoes — stop-of-A (position/played) and start-of-B (Jellyfin stamps PlayCount+LastPlayedDate at start; visible in the log payloads) — arriving seconds apart, so each lands in its own 2 s-tick cycle: two probe scans, two music-widget re-fetches. On top of that, Kodi natively re-fetches every `SortByNone` widget on `Player.OnPlay` and its own end-of-song playcount write announces `AudioLibrary.OnUpdate`. That stack — native OnPlay + native OnUpdate + echo-A cycle + echo-B cycle — is the observed "double refresh on next track", and only the last two are kofin's to fix (D3/D2); the native pair is reachable only from the skin (D7).

F4 — `touched_databases` means "a writer thread started", not "rows changed" (`worker_updates`/`start_writers` add the db before a single item is written). A cycle whose items all short-circuit (`fields.check_unchanged` Etag matches; userdata echoes rewriting the values Kodi already has — the userdata writers compare nothing before writing, `writers/movies.py userdata`) still ends in a refresh. This is the class the fingerprint gate exists for.

F5 — removing a music library never refreshes music. `FullSync.remove_library` refreshes nothing itself; the only refresh after a RemoveLibrary command is the F1 tail, whose fallback is `{"video"}` — removed albums linger in the music widgets until some later music refresh. (Repair of a music library survives only because the re-add's FullSync refreshes music.)

F6 — the first-sync `ReloadSkin()` is the right mechanism (see the deaf-provider and include-condition facts above) but has two reliability gaps: the fixed `waitForAbort(2)` between the no-op scan and the reload is a race (a slow box that hasn't flipped `Library.HasContent` yet rebuilds the skin against the old bools, and the check is self-disarming so it never retries), and there is no music equivalent at all — `_video_content_hidden` probes only MyVideos, so a first *music* sync (video already populated or never selected) leaves the music widget sections unbuilt until something else reloads the skin.

F7 — refresh-when-needed audit is otherwise clean: additions are strictly prioritized, `refresh_added` makes them visible as soon as the last added write lands (gated exactly like the new-content toast), the end-of-cycle refresh covers everything else, boxset/divergence heals arrive via UpdateLibrary commands (F1/F2 costs aside), and `views_hash` handles node regeneration. The incremental-scan answer the audit was asked for: yes — widgets refresh when the *added* class completes (before updates/artwork drain), and again at cycle end only if more was written after that point (`added_databases`/`touched_databases` bookkeeping at `:993-1000`).

F8 — `Container.Refresh` fires for any media window on any refresh, even when the window's content has nothing to do with the database that moved (a music echo cycle refreshes the movie listing you are browsing; a plugin listing re-fetches from the server).

F9 — screensaver interaction, live-confirmed 2026-08-04 on the local box (Dim saver, 1 min, `dbSyncScreensaver` at its default true). An active screensaver has zero effect on sync: a server-side favorite toggle arrived over the websocket in under a second, the userdata writer wrote MyVideos, the watermark advanced and the end-of-cycle refresh fired, all with the saver up — nothing in kofin gates on `System.ScreenSaverActive`, and the socket stayed connected throughout. Each *wake* fires the F1 stack: `GUI.OnScreensaverDeactivated` → FastSync → tail `UpdateLibrary(video)` *before* any queued write lands, then the drain refresh — a wake that replayed one already-applied userdata record (the watermark deliberately lags, and the writers write blind, F4) produced two no-op `VideoInfoScanner` passes at the exact moment the user looks at the screen, and any input that interrupts the saver counts (an EventServer packet did). Two side findings: the tail's `update_status_strings` rewrites addon settings on every command, observed racing Kodi's settings persistence into a transient "failed to load addon settings" (absorbed by the applier's deviceId guard); and the `dbSyncScreensaver` help text (30309) promises the catch-up "always runs when the screensaver ends" while the code runs it only when the setting is true.

## Plan

D1 — refresh ledger stays, gate moves to evidence. Keep `touched_databases`/`added_databases` as the *candidate* signal (which databases might need a refresh), but make the actual firing conditional on a widget fingerprint moving. No transplant writer grows change-reporting: the gate reads the databases after the fact, so `sync/writers/` and `sync/kodidb/` stay byte-faithful to the fork.

D2 — `sync/widgetstate.py` (new, shell dialect): per-database fingerprints of exactly what home widgets render, the pvr.kofin contract translated. Video: the ordered id list + (title, art urls, dateAdded) of the top-N by dateAdded for movies and episodes (recently-added widgets), the ordered in-progress lists with resume rounded to whole percent (progress bars), and a whole-table (id, playcount>0, resume>0) map for watched-overlay state (any widget can render any item's overlay — random widgets included). Music: ordered top-N album lists for recently-added and recently-played (album id + art + the *order*, never the raw lastplayed timestamp — a timestamp bump that reorders nothing must not read as change), plus the (idSong, iTimesPlayed) map. Fingerprints are instance state on `Library` (restart-safe by the no-module-global rule); an unknown fingerprint always refreshes once, exactly like pvr.kofin's first poll. Each hashed field carries the maintenance note pvr.kofin's header has: a field widgets render but this module does not hash is a stale-widget bug, and the L2-style tests below are the enforcement.

D3 — coalesce cycles before gating them. A drain that completes arms a short settle (`REFRESH_SETTLE_SECONDS ≈ 4`, service tick is 2 s) instead of refreshing inline; work arriving inside the settle folds into the same eventual refresh. This alone turns F3's two echo cycles into one refresh, and the D2 gate then decides whether even that one fires (same-album playlists: order stable → zero). `refresh_added` keeps its immediate path — new-content visibility is the feature and is worth one refresh by definition — but consults the gate too (an addition always moves the fingerprint, so this costs nothing in practice).

D4 — every command path owns its refresh; the `process_commands` tail refresh is deleted. FullSync refreshes only when it wrote (skip the `start()` refresh in update-mode plan-only passes — the drain owns it); `remove_library` refreshes the removed library's own database kind (fixes F5); FastSync and the playlist commands refresh nothing. Fixes F1/F2 outright: a screensaver wake or reconnect with nothing new becomes zero builtins.

D5 — first-sync reload made reliable (F6): replace the fixed 2 s wait with a poll of `Library.HasContent(...)` (250 ms steps, ~10 s ceiling, then reload anyway and log); extend the hidden-content probe to music (`_music_content_hidden`: MyMusic has album/song rows while `Library.HasContent(Music)` is false → same scan-then-reload path); defer the reload while video is playing fullscreen (hold like `notify_new_content` holds toasts, reload at stop). ReloadSkin itself stays — the audit found no substitute, and the answer to "is there a better way" is no: everything else cannot rebuild condition-gated includes or wake deaf empty providers.

D6 — scope `Container.Refresh` to the window it helps (F8): fire it only when the front media window's path family matches a database the gate says moved (`videodb://`/`library://video`/video `.xsp` ↔ video; `musicdb://`/`library://music` ↔ music; `plugin://plugin.video.kofin` browse listings refresh on either, they are server-backed).

D7 — skin follow-up, separate repo, recorded here because it owns the *native* half of F3: give contuary's widget includes explicit `sortby` params so their providers stop being `SortByNone` and are no longer re-fetched on every `Player.OnPlay`/`OnStop`; keep lastplayed/in-progress widgets on their sort (that invalidation is the feature). Kofin cannot influence this from the addon side.

D8 — considered and rejected: window-property reload stamps (native db containers cannot bind a cache-buster; only plugin-path widgets could, and contuary uses none), per-widget refresh addressing (Kodi has none — announcement invalidation per media kind is the floor), suppressing refreshes during local music playback (Kodi natively re-fetches `SortByNone` widgets per track anyway, and it would starve legitimate mid-session updates; D3's settle is the honest version).

D9 — the screensaver paths, resolved by F9 and **done ahead of the rest of phase 1** (2026-08-04): the `dbSyncScreensaver` setting is removed outright. The saver needs no accommodation for *correctness* (sync runs under it, and an interrupted sync is survivable by design — sync.json resume plus idempotent writers — which retires the fork-era reason for fighting the screensaver), so the whole inhibit path went: both copies (`library.py`'s per-cycle one and `FullSync.__enter__`/`__exit__`'s), the `screensaver` attributes, the `get_screensaver`/`set_screensaver` shims, the `InhibitIdleShutdown` calls, the settings.xml entry and strings 30308/30309. This also deletes the latent hazard where a Kodi quit mid-sync (with the setting off) permanently lost the user's `screensaver.mode` — the restore only ran on the drain path. The wake FastSync stays and is now unconditional, as help 30309 always claimed: it is the only cover for a *silently* half-open websocket after long idle — `_catch_up_after_reconnect` covers only detected drops — and once D4 removes the tail refresh an empty wake catch-up costs one HTTP request and zero UI. Still owed by phase 1: `update_status_strings` moves to write-on-change so command processing stops rewriting the settings file it immediately re-reads.

## Phasing and gates

Phase 1 (D4, D5, D9): command refresh ownership + reload reliability + screensaver cleanup (the D9 removal itself already landed, 2026-08-04). Live gates: screensaver wake with a quiet server → zero `UpdateLibrary` builtins (baseline live-verified 2026-08-04: two no-op scans per wake); wake catch-up runs on every wake with no setting involved (live-verified at removal); per-library update command → exactly one probe scan (was two, log-verified); remove a music library → albums leave the music widgets without a restart; fresh-profile first video sync and first music-only sync → widgets appear with no manual reload, reload deferred if video is playing.

Phase 2 (D3): settle/coalesce. Live gate: music playlist next-track → at most one kofin-originated music refresh in the log (two echo events, one probe scan); video stop → one video refresh.

Phase 3 (D2, D6): fingerprint gate + container scoping. Live gates: replayed unchanged echo (pause/unpause, same-album next-track) → zero builtins; new movie via FastSync → refresh within the cycle; artwork-only tier-1 update → refresh fires (art is hashed); browsing movies during a music-only cycle → no `Container.Refresh` on the movie window. L1/L2: fingerprint module tested against the pristine schema fixtures — write a movie, fingerprint moves; rewrite identical userdata, fingerprint holds; reorder recently-played, music fingerprint moves; every gated schema parameterized like `test_sync_writers.py`.

Phase 4: docs — CLAUDE.md constraint bullet (fingerprint fields must cover widget-rendered fields; the settle must never be re-inlined "for snappiness"; the tail refresh must not come back), testing-plan rows for the gates above, and this plan updated with as-built deviations.

Measurement across all phases: count `UpdateLibrary`/probe-scan/`Container.Refresh` lines in kodi.log per scenario before and after (the probe scan's "does not exist - skipping scan" line is a reliable marker; add a one-line INFO log per fired/suppressed refresh with the moved fingerprint sections so suppression is auditable).

## As built (phases 1–3 implemented 2026-08-04, stacked PRs)

All three implementation phases landed as designed — D9 first (the setting removal, committed ahead on the phase-1 branch), then D4/D5, D3, and D2/D6 — with these deviations and decisions worth recording:

- The music fingerprint hashes the recently-added and recently-played *album orders* plus the reference checksums, and deliberately nothing per-song: raw play counts and lastplayed values move on every echo while contuary renders neither, which is what makes the same-album-replay case a zero-refresh cycle. A skin that renders play counts on Home (Estuary-style "most played" rows) would need a section added — the module docstring carries the contract.
- The video ``userdata`` section carries the movie→set link (``idSet``), so boxset membership healing refreshes without the reference checksums moving (the memberless-set NULL-checksum rule means reference digests deliberately cannot see membership).
- Fingerprint reads take no process lock: every ``Database`` connection runs WAL, so the reads never block a mid-drain writer and the service tick never stalls behind one; a mid-drain snapshot at worst costs one extra refresh when that drain completes and re-arms the settle. Kodi-native writes (Kodi marking watched itself) land between refreshes and read as moved on the next echo cycle — one refresh where none was strictly needed, accepted as the residual.
- ``_moved_databases`` never opens MyMusic when the whitelist has no music library (the ``check_version`` rule); the refresh passes through ungated instead.
- Settle constants: 4 s settle re-armed per drain, 15 s hold cap from the first deferral; the immediate paths (``refresh_added``, command-owned refreshes) clear the deferred debt for their databases so nothing fires twice.
- The first-content reload polls ``Library.HasContent`` at 250 ms up to 10 s and then reloads anyway (a late reload beats an invisible section); it is held during video playback and flushed by the service tick at stop.
- Phase-4 constraint bullets live in CLAUDE.md; the live gates are W1–W7 in docs/testing-plan.md, pending their first full run.
