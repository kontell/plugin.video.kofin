# Offline downloads: feasibility study

Research study for "download for offline viewing" (2026-08-08). Sources: live experiments against the local Kodi (kofin-test profile, Omega, MyVideos131/MyMusic83) and the real server (Jellyfin 10.11.11), the Jellyfin server source, Kodi Omega source, and deep reads of kodi-jellyfin-downloader, plugin.video.emby (next-gen), jellyfin-android v2.7.0, Finamp's downloads rewrite, Findroid, Streamyfin, Swiftfin and jellyfin-web. Everything marked **[live]** was measured on this box during the study; the raw session artifacts (restore scripts, the experimental play-route patch, screenshots) were left in the session scratchpad.

## Verdict

Feasible, and the shape is clearer than expected: **download originals over `/Items/{id}/Download` with the existing user session, repoint the Kodi library rows at the local files (the Emby-for-Kodi model, live-validated here), tag downloaded items into a generated Downloads node, and queue offline userdata for replay**. Synced libraries only. No part of this fights Kodi; every hard sub-problem has either a live proof below or a shipping precedent. The genuinely novel parts — offline watched-state replay done properly, and auto-download-next-episode — exist in no Jellyfin client today; kofin would be first.

## Can an offline Kodi be simulated? (asked up front)

Yes, without sudo, with one caveat. Passwordless sudo is not available to the assistant, so the gold-standard simulation (an nft rule dropping traffic to the server, **port-scoped** because the same host serves NFS) could not be installed. What worked instead: quit Kodi, point the kofin-test profile's `serverAddress` at `10.255.255.1` (a blackhole — connect hangs exactly like a firewall DROP), relaunch. That faithfully simulates "server gone" for everything that reads kofin's credentials: the service, the websocket, every plugin route. The caveat: rows holding **absolute server URLs** (direct-mode music, cached art URLs) still reached the real server, so the music-offline test blackholed one song's own path row as well. A future full-fidelity pass just needs the user to run the port-scoped nft rule; nothing observed suggests it would change any conclusion.

## Live verification results

**V1 — the download endpoint works on the user session.** `/Items/{id}/Download` with a plain `MediaBrowser Token` header (no api key): HTTP 206 on a Range request, `Accept-Ranges: bytes`, exact `Content-Length`, and `Content-Disposition` carrying the server-side original filename. Gated on the user's `EnableContentDownloading` policy (default **true**; confirmed true for kofin-test), verified in server source: `Policies.Download` → `UserPermissionRequirement(PermissionKind.EnableContentDownloading)`, plus a per-item `CanDownload` that is true for Video/Audio and false for folders — so season/series/album downloads are always client-side expansion. Resume = `Range: bytes=<size>-`, and HTTP 416 means already-complete (jellyfin-android's convention).

**V2 — transcoded downloads are a batch job, not a realtime tail.** A progressive `/Videos/{id}/stream.mkv` transcode (h264, 2 Mbps, `allowVideoStreamCopy=false`) delivered **189 MB in 25 s ≈ 28× realtime** on the server's hardware. This matches server source: `EnableThrottling` defaults false and 10.11 ships migration `20250420050000_DisableTranscodingThrottling` force-disabling it everywhere. `DELETE /Videos/ActiveEncodings?deviceId&playSessionId` returned 204 and killed the job; closing the connection also ends it.

**V3 — the transcode-download container is load-bearing: mkv fails, fragmented MP4 wins (amended 2026-08-08).** The progressive **mkv** transcode saved to disk had no duration header and no cues (ffmpeg cannot seek back on a socket): Kodi reported `totaltime 0:00`, refused to seek, and mis-marked the item watched on stop. The same content as **`stream.ts`** worked fully (duration, instant seek, clean resume bookmark) — but TS measures **+5.0 % container overhead** and has no AV1 mapping at all. The follow-up test settled the better option: Jellyfin emits progressive mp4 as **fragmented MP4** (`-movflags frag_keyframe+empty_moov+delay_moov`, `EncodingHelper.cs:7615` — this study's first draft claimed "no moov atom → unplayable", which was wrong), and a `stream.mp4` pull cut off mid-stream with no finalize still ffprobed at its full duration and, in Kodi, showed 11:55 total and took a mid seek (6:40→6:42) and a deep seek (11:00→11:02) cleanly. Measured overhead ≈ **0.0 %** (266,178 B/s against a 2,129 kbps elementary stream, vs TS's 279,520 B/s for the same content). Rule: original downloads keep their container; transcoded video downloads are fragmented MP4 — which also unblocks AV1, since no standard AV1-in-TS mapping exists while AV1-in-MP4 is standard and kofin's device profile already ships an AV1 fMP4 HLS leg for streaming.

**V4 — the repoint model works end-to-end, offline.** With a movie's `files` row repointed at a local file (`files.idPath` → a path row for the downloads dir, `strFilename` = basename): browse → play → seek → stop → **resume bookmark 408/694 s written to the item's own file row** → reopen with resume → playback resumed at the bookmark — all with the server blackholed, all through the untouched library UI. Music equally: a song row repointed (path row + filename; MyMusic has no full-URL-wins arm, `CVideoDatabase::ConstructPath` does) played the local file through `musicdb://`. And while **online**, a repointed play still reported to the server correctly — the service's backfill claims by Kodi dbid, not by path, so scrobbling survives the repoint untouched.

**V5 — the *naive* repoint corrupts identity; the full one is mandatory.** Leaving `files.idPath` on the plugin path row and writing an absolute path into `strFilename` plays fine (ConstructPath returns it as-is when the path row is `plugin://`), but Kodi's save-state resolves the played path canonically (parent dir + basename) and **wrote `playCount` to a freshly inserted shadow files row** under a new path row. Watched/resume silently land off the library row. plugin.video.emby's `get_add_path` + `replace_PathId` dance exists precisely for this; kofin must do the same. Kofin has one structural advantage over Emby here: the original plugin path needs no stored backup — the writers can re-derive it from the jellyfin id deterministically, so "remove download" is a re-stamp, not a restore-from-record.

**V6 — the offline sync-back insertion point already exists and currently loses the event.** Playing a downloaded episode to the end offline: Kodi announced `VideoLibrary.OnUpdate`, kofin's `service/kodiuserdata.py` picked it up (`kodi episode 12910 played=True`), tried `mark_played`, got `ServerUnreachable` after one 6 s connect attempt, logged "kodi userdata push failed", and dropped it. The watched flag never reaches the server and nothing retries. The pending-userdata queue belongs exactly at that failure point (and at `service/player.py`'s report failures).

**V7 — offline browse is a non-event.** With the server unreachable: the addon stays visible and enabled (the "addons sometimes not visible" worry did not reproduce for an installed addon); library nodes list instantly (139 ms for a tag node, 35 ms for show → seasons); posters render from Kodi's texture cache; drill-down show → season → episodes is fully local. The tag experiment — a `Kofin Downloads` tag row linked to a movie and a show plus a three-file node folder with a `field=tag` rule — produced a working "Downloaded movies"/"Downloaded shows" tree next to kofin's generated nodes, online and offline, screenshot-verified. This is the same machinery kofin's views already use (every view is a tag; favorites are synthetic tags), so the Downloads node is incremental, not new.

**V8 — offline failure modes, measured.** Non-downloaded plugin item: click → spinner → kofin error toast at **~8 s** (plugin interpreter start ≈1.5 s + two 3.05 s interactive connect attempts). Direct-URL music row: **30 s silent hang** (CCurlFile timeout) then playback simply never starts, no toast at all — the single worst UX found, and the strongest argument for both the music repoint and an offline-mode fast-fail. The kofin plugin root offline: 7.4 s, then renders its static entries (Continue watching, Who's watching?, SyncPlay, Settings). Cold boot offline: service start → first "server not reachable" warning ~30 s later, then quiet log-only backoff (5 s doubling to 120 s); no toasts, because connection toasts ride websocket events and the socket never connected.

**V9 — two real defects surfaced by the offline runs (both present in current `main`).** (a) The service's `_connect` probe runs on the service main thread with the transport's default budget: offline, each probe **blocks the service loop for ~29 s** (4 × 6 s connect + backoff). During a profile switch, Kodi stopped services while kofin sat inside that ladder; it blew the 5-second grace ("script didn't stop in 5 seconds - let's kill it"), and the interrupted login left the profile with **no kofin service and a dead webserver** — Kodi had to be killed. The transport's `abort` predicate reads only `Service._stopping`, which rises in `_shutdown`; a Kodi-side `abortRequested` during `_connect` is invisible to it. Fix independently of this feature: the abort predicate should also consult `Monitor.abortRequested()`, and the connect probe deserves the interactive budget or its own thread. (b) Separately, an **online** quit wedged for 2+ minutes with a websocket thread still dispatching `LibraryChanged` a full minute after "Application stopped" (installed 0.12.0; SIGKILL required). Offline steady-state quits were clean — the wedge is the ws/library path, not the offline path.

**Not live-verified (blocked or out of scope), and how to close each.** The alternative *plugin-route* playback design (resolve to the local file inside `mode=play`) could not be deployed: the permission classifier denied both editing the installed tree and running `tools/dev-install.sh`. The patch is written and saved (`play-local-shortcircuit.patch` in the session scratchpad); apply it and run `tools/dev-install.sh` to A/B it in five minutes. Full-host offline (art fetches, every direct URL at once) needs the sudo port-scoped firewall rule. Android external-SD behavior was not tested — no Android box was driven this session; the Piers Bravia is reachable over ADB for a follow-up.

## What the other implementations teach

**kodi-jellyfin-downloader** (the independent implementation): a context-menu script whose whole existence depends on an **admin API key** because it has no session — it calls admin-gated `/Users` just to invent a userId, so all its watched filtering runs as the wrong user. Sequential, no resume (writes directly to the final filename, so a crash leaves a truncated file treated as complete forever), no verification, one failure aborts the queue, NFOs without uniqueids, and its offline browse story is "make a second Kodi profile and scan the folder". Worth keeping: the external-subtitle endpoint family (`/Videos/{id}/{sourceId}/Subtitles/{index}/Stream.{ext}`, `subrip`→`srt`), server-side `Filters=IsUnplayed` for bulk-unwatched queues, requesting `MediaSources` in the listing fields to avoid per-item round trips, and the reminder that reverse proxies can drop the Authorization header across redirects. Everything else is superseded by kofin having a session, kofin.db, and a service.

**plugin.video.emby next-gen** is the proven Kodi-native template and the strongest single precedent: download to a gated folder, **repoint the Kodi path/file rows, keep a restore record, re-cache artwork locally, reverse on delete** — plus a free-space reserve check and a dedicated download worker with its own HTTP connection. V4/V5 above independently reproduced why every piece of that design exists.

**jellyfin-android v2.7.0**: own OkHttp downloader + WorkManager (they *abandoned* both Android's DownloadManager and ExoPlayer's), Range-resume with 416-as-complete, a two-table Room DB snapshotting the full item DTO for offline rendering, verify-by-size before trusting any file, `.nomedia` in the tree, SAF folder choice. Headline gap: **no offline playstate tracking at all** — resume/watched are announced as future work.

**Finamp** (music reference): reliability came from one normalized download graph in a real DB — membership, refcounting, ordering and status all derived from links; deletion is unlink + reachability sweep; intents persist before links change so crashes strand nothing; paths stored relative and re-derived at startup; a user-invokable repair that re-verifies every file and sweeps orphans. Three profiles per node (user-requested / effective / on-disk transcode quality) make quality changes a diff, not a re-download-everything. Offline plays are an exportable log, **never** replayed to the server; offline favoriting is refused. Their migration war stories (a wrongly-defaulted "already migrated" flag silently skipping migration for a year) argue for boring, explicit download-store versioning.

**Findroid / Streamyfin / Swiftfin / web**: Findroid is the only client that replays offline userdata (`toBeSynced` flag → `POST /Items/{id}/UserData`, blind last-writer-wins — their #406 ghost: played=true *plus* a stale position resurrects items into Continue Watching; replaying both fields in one call avoids it). Streamyfin invented the transcode-download flow kofin should copy (PlaybackInfo → rewrite `master.m3u8`→`stream` in the TranscodingUrl → pull progressive ts) and keeps offline progress device-local forever. Swiftfin has no downloads. jellyfin-web is browser-download only. **No client has auto-download-next or smart deletion; there is no server-side download registry or offline-sync API (Emby's Sync was removed), and no server-side folder download.**

## Design

**Scope: synced libraries only.** Agreed, and not only because storage-poor boxes are the dynamic-mode audience: every good thing in this design — native offline browse, tags, Kodi-owned resume/watched, the userdata echo loop — hangs off library rows that dynamic mode does not have. A dynamic-mode "Downloads" plugin folder could be bolted on later; it is a separate, lesser feature and should not shape this one.

**State: a `download` table in kofin.db.** Columns roughly: jellyfin_id, media_type, state (queued/downloading/done/failed), origin (context/auto-next/collection id, for Finamp-style "why is this here" and safe deletion when two origins overlap), local relative path, container, size expected/actual, quality profile used, bytes done (resume), userdata snapshot at queue time, timestamps. The store's location setting holds the root; paths stored relative (Finamp's lesson — survives moving the root). sync.json stays what it is; downloads get their own queue because entries leave it on user action, not on server ack.

**Files: human-readable from day one.** It costs one sanitization function and nothing else — the server hands over its own filename in `Content-Disposition`. Layout: `Movies/Title (Year)/<original filename>`, `TV/Show/Season NN/<original filename>`, `Music/AlbumArtist/Album/NN Title.ext`. Names frozen at download time (no rename-on-metadata-change). Sanitize for FAT/exFAT (Android SD), warn on >4 GB originals targeting FAT32. Optional "export metadata for other apps" toggle writes NFO **with uniqueids** (the downloader repo's NFOs omit them and are a dead end) plus `poster.jpg`/`fanart.jpg`; cheap, off by default, and makes the tree scannable by any Kodi/Plex/Infuse as a bonus escape hatch.

**Playback: full repoint, not a play-route branch.** The repoint (V4) gives offline resume prompts, watched marking, instant starts (no 1.3–1.7 s interpreter tax per play on no-invoker-reuse boxes), works identically for direct-mode music rows that never touch the plugin, and keeps online reporting intact via the dbid backfill. The mandatory shape (V5): ensure one path row per downloads subfolder (with the same `strContent`/scraper stamps the show's plugin path row carries, per the tvshows-writer constraint), repoint `files.idPath`, set `strFilename` to the basename. Remove-download reverses it by re-running the writers' own path construction — no stored original needed. The writers' idempotency suite must learn that a downloaded item's path row is *expected* to differ (compare-masked, like the music `dateNew` case), and removal must restore byte-identical rows — that is the L2 test for this feature.

**Context menu: three entries in `_manage_options`.** "Download" (item not in store), "Cancel download" (queued/active), "Remove download" (done) — gated on a downloads-enabled setting and on `item.CanDownload` the same way delete gates on `CanDelete` (the server names the permission; a 403 here means the admin turned `EnableContentDownloading` off, and the entry should not have been offered). Series/season/album/artist/playlist entries expand client-side through the existing paged `downloader.get_items` (arity rule applies). Size preview comes free: `MediaSources` already rides the manage() item fetch. The manage() menu itself needs the offline-mode guard — today it round-trips the server before showing anything, so offline it dies in a toast even when the only wanted action is "Remove download"; offline, build the menu from the store alone.

**Transcode option: a Downloads settings group, fragmented-MP4 container, PlaybackInfo-driven.** Quality choices: Original (default) or a max-bitrate list reusing the transcode tab's vocabulary (`preferredVideoCodec`/`preferredAudioCodec`/`maxResolution` reused as-is, plus a downloads-own max bitrate — mirroring how contextBitrates already works). Implementation is Streamyfin's: PlaybackInfo with a download device profile (video `TranscodingProfiles` with `Protocol: "http"`, `Container: "mp4"` — the server muxes progressive mp4 as fMP4, V3, and deviceprofile.py already builds the music http profile this way), then pull `TranscodingUrl` with `master.m3u8`→`stream` rewritten, `deviceId`+`PlaySessionId` kept, `DELETE /Videos/ActiveEncodings` on cancel/failure. fMP4 rather than Streamyfin's ts, for measured reasons (V3): 5 % smaller on disk and it carries AV1 — so the AV1 choice the preferred-codec spinner already offers works for downloads too, when the server has an AV1 encoder configured (and expect AV1 encodes to run far below the 28× h264 rate; the flat-out advantage is encoder-bound). Transcodes are not Range-resumable (a re-encode is not byte-stable) — restart on failure, and cap **concurrent transcode downloads at 1**: V2 showed the server encodes flat-out with no throttle, so two parallel transcode pulls would saturate the server's encoder unbidden. Completion check: originals verify size == Content-Length; transcodes have no Content-Length, so completion = clean EOF plus a duration probe against the item's runtime.

**Download manager: a service worker, kofin.db-queued, abort-correct.** A worker pool in the service (`maxParallelDownloads` setting, default 2 originals; transcodes serialized as above), each worker on its own `_new_api()` session so the abort predicate reaches it, chunk loop checking the stop flag every chunk (a 30 s read timeout bounds a dead socket; V9's lesson applies doubly to multi-GB reads). Stream to `<name>.part`, rename on verified completion — never the downloader repo's write-to-final-name. Free-space precheck (Emby's 2 GB reserve + expected size). Progress: a window property for skins plus completion/failure toasts; no blocking dialogs. Retry with backoff for originals (Range-resume from bytes done); queue survives restarts by construction (it is a table). Widget/refresh integration: download completion and removal fire their own `refresh_libraries` the way command paths own their refreshes — never a blanket refresh.

**Downloads node: the tag, stamped to survive resync.** Stamp a `Kofin Downloads` tag (label via `strings.po`, but the node XML value is the tag string — `_node_label` rules apply to the `<label>`) on downloaded movies/episodes and their shows; generate a Downloads node folder (movies + shows) in `sync/views.py` and bump `NODE_LAYOUT`. Critical: writers replace tag sets on every item write, so the tag must be injected where favorites inject theirs (`writers/movies.py:160` pattern) from a downloads-store lookup, or the next sync of a downloaded item silently untags it. This touches transplant code the way the favorites feature already does — same injection point, same shape, covered by extending the L2 full-fidelity cases.

**Offline mode: make `kofin.online` honest, then spend it everywhere.** Today the flag latches true on first connect by design (`library.py` documents it). The feature needs a real signal: lower it on websocket disconnect + a failed short probe, raise it on reconnect (the existing backoff/connect loop and wake-time FastSync already provide the edges — the flag write is the only new part; the unconditional wake FastSync stays untouched). Spend it: the play route answers "not downloaded + offline" in <2 s with an honest toast instead of V8's 8 s spinner; manage() builds the local-only menu; `kodiuserdata`/player reporting skip straight to the queue instead of eating 6 s timeouts per event; the service `_connect` probe gets the interactive budget so the loop never blocks 29 s (V9a's fix). Root listing already degrades acceptably. Direct-URL music that is not downloaded keeps V8's ugly 30 s hang — unfixable from kofin's side (Kodi's curl owns it), which is an argument for surfacing downloads prominently in music mode, not for heroics.

**Watched-status sync-back: queue + replay-then-FastSync.** A `pending_userdata` table (item id, played/position/favorite deltas, event time, the item's server-userdata snapshot from download time). Fill it where V6 showed events dying. On reconnect, replay **before** the catch-up FastSync so the server echoes overwrite local state only after our writes land: position+played travel in one `POST /Items/{id}/UserData` (dodges Findroid's #406), bare toggles via the existing documented routes. Conflict policy better than the field standard at near-zero cost: if the server's `LastPlayedDate` moved past our snapshot (someone watched elsewhere while we were offline), prefer the further position and drop stale deltas; otherwise last-writer-wins. The echo loop terminates for the same reason it always does — replayed writes come back as `UserDataChanged` and are applied via announcement-free SQLite.

**Auto-download next episode: a service hook, first in the ecosystem.** On playback progress of a downloaded episode crossing ~80 % (the player already tracks position), queue the next unwatched episode of that show at the same quality (`adjacent_episodes` exists in `core/api.py`). Retention as separate settings: keep-next-N (default 2), delete-watched-after-N-days (default off — deletion is the user's call until trust is earned). Both live under the downloads settings group; the delete pass runs in the manager worker and respects the tag/repoint reversal path. Composes naturally with a later "download whole season/show and keep it current" collection mode (Finamp's collection-sync shape).

**Transcoded music downloads are in scope, not optional** (decided 2026-08-08: FLAC → 128 kbps Opus is a ~6–8× saving, and there may be a lot of them). Same flow as video with one difference in its favour: the music TranscodingProfile kofin already builds is plain-http progressive (`play.mime_for` documents it), so the PlaybackInfo → `TranscodingUrl` pull needs no `master.m3u8` rewrite — and the V3 ts-container rule is a video problem, since an Ogg/Opus stream written to disk is complete and seekable as-is. Downloads get their own quality pair in the downloads settings group (Original / codec+bitrate spinners mirroring the music streaming tab's vocabulary; Opus 128 kbps is the intended default saving), the per-download container is recorded in the download row and stamped into the repointed `strFileName` (the musicdb extension rule), and abandoned jobs are closed the way video's are — `deviceId`+`PlaySessionId` on the request, `DELETE /Videos/ActiveEncodings` on cancel, which kills audio jobs too (`KillTranscodingJobs` matches by device/session, not media type). Two implementation checks flagged for build time: verify the server's ffmpeg maps FLAC tags into Vorbis comments on 10.11 (expected, but the offline tree's usefulness to other apps depends on it), and expect embedded cover art *not* to survive a streamed transcode — Kodi renders from its own art database regardless, and the optional `folder.jpg` export covers everything else.

**Music: repoint carries it further than expected.** Downloads of tracks/albums/artists/playlists expand client-side to track lists; each track downloads as an original (metadata embedded — the server serves the tagged file bytes; transcoded audio via `/Audio/{id}/stream` keeps tags through ffmpeg) and repoints its song row — which works in **both** path modes (V4), so the feature does not need `musicTranscode` enabled, contra the initial assumption. Browse-after-download: the normal music library keeps working (downloaded tracks play locally, others fail per V8), and since repointed songs' *paths* now live under the downloads root, a **smart playlist with a path-startswith rule** gives a real "Downloaded music" view with zero schema tricks — it lives in the `Kofin/` playlists folder, so `sync/playlists.py` must add it to the prune exemption the same way the folder icon is exempted. Album art is already in Kodi's DB/texture cache; `folder.jpg` export is part of the optional metadata-export toggle. Per-song path rows make the repoint one-row-per-track; the restore is the writers' own path stamp, and the musicdb extension rule holds because original filenames keep their extensions.

**Storage location & Android.** A `type="path"` downloads-root setting (Kodi's own folder browser), default under the profile's addon_data. On Android the app-specific external dir (`/storage/<uuid>/Android/data/org.xbmc.kodi/files/`) is writable without SAF or permissions and is the documented answer for SD cards; the setting's apply-path does a write-probe and reports failure immediately rather than at first download. Free-space shown via `os.statvfs` at pick time. Downloads run in the service process with plain `requests` streaming to POSIX paths — Kodi on Android exposes real paths, so no `content://` handling is needed (jellyfin-android's SAF machinery is an Android-app constraint kofin does not have).

**Sync interactions.** A downloaded item's library row still syncs metadata normally (the writers only repoint path columns the download owns; checksums/Etags continue to flow). A server-side delete of a downloaded item follows the existing removal path but must also delete the local file and store row — or, better, offer to keep it as an orphan export; V1 keeps this rare. `views_hash` bumps with the node addition; `verify_kodi_defaults` untouched. The drift probes (boxsets) are unaffected — downloads never touch `idSet`.

## Bugs found along the way (independent of the feature)

The V9a service-thread connect ladder (blocks the loop ~29 s per offline probe; invisible to Kodi's `abortRequested`; wrecked a profile switch to the point of a dead webserver) and the V9b online-quit websocket wedge ("Application stopped" with a kofin ws thread still applying `LibraryChanged` a minute later, SIGKILL needed — observed on installed 0.12.0). Both are worth fixing before the downloads feature multiplies time spent in the unreachable-server paths.

Both are now fixed (2026-08-08, same-day follow-up): (a) the transport abort predicate became `Service._abort_transport` (`_stopping` folded with `abortRequested()`) on every session the service builds, and `_connect` probes on `Api.probe_info`'s single-attempt 3.05 s budget; (b) `WSClient` gained a dispatch gate (a stopped client hands its owner nothing, and a connect landing after `stop()` spawns nothing), `stop()` escalates to a raw-socket `shutdown()` when the graceful close leaves the receive thread blocked, and `_shutdown` stops the websocket before the library join so no event races the teardown. Regression tests pin each piece (`test_service.py`, `test_ws.py`, `test_api.py`); the CLAUDE.md thread-stop bullet records the amended contracts.

## Phasing sketch

Phase 1 — originals for movies/episodes: kofin.db download table, service download worker (parallelism, resume, verify, .part+rename), context-menu entries, full repoint + reversal, `Kofin Downloads` tag + generated node + NODE_LAYOUT bump, writer tag-injection + L2 cases. Phase 2 — offline correctness: honest online flag, fast-fail play route and offline manage(), pending_userdata queue + replay-then-FastSync. Phase 3 — transcoded downloads (fragmented MP4, PlaybackInfo-driven, encoder cap) and music (tracks→playlists, smart-playlist view, prune exemption, and Opus transcode downloads as a requirement — FLAC-heavy libraries are exactly the size problem downloads exist to manage). Phase 4 — auto-next + retention, optional NFO/art export, collection keep-current mode. Live gates per phase belong in docs/testing-plan.md; the offline scenarios in this study (V4–V8) are the phase-2 gate almost verbatim.

## Decisions (answered 2026-08-08)

"Remove download" is always available in the context menu. The original question's "Android-style long-press" framing was a confusion of this study's, not a real design axis: Kodi's context menu is one surface on every platform (long-press is merely how touch invokes it), so there was never a platform split to design for. The entries live in the Jellyfin actions menu wherever the item appears — the Downloads node included — and the offline manage() path keeps Remove working with the server unreachable.

Transcoded music downloads are in scope, not optional — see the music transcode paragraph in the design section (FLAC → 128 kbps Opus, ~6–8× smaller).

Still assumed rather than decided: the optional NFO/art export writes into the media tree (scannable by other apps, slightly noisy) rather than a parallel `metadata/` tree.
