# Offline downloads: implementation plan

Implementation plan for the download-for-offline feature. The evidence base is docs/offline-downloads-feasibility.md — its V-numbered live findings are cited here as V1…V9 and not restated; where this plan asserts something about Kodi or the server, the proof lives there. Decisions already made with the user: synced libraries only; the repoint model, not a play-route branch (V4/V5); Download/Cancel/Remove live in the Jellyfin actions menu everywhere, including the Downloads node; transcoded music (FLAC → 128 kbps Opus) is a requirement; transcoded video downloads use fragmented MP4 (V3, amended).

## Shape

Four phases, each shippable alone. Phase 1: original-quality downloads for movies and episodes, repointed into the library, browsable under a Downloads node, with a real download manager in the service. Phase 2: offline correctness — an honest online flag, fast failure, and the pending-userdata queue with replay. Phase 3: transcoded downloads (video fMP4, music Opus) and music downloads generally. Phase 4: auto-download-next, retention, and the optional metadata export. One feature branch per phase (`feat/downloads-p1` …), each landing with its unit tests green and its live gates run.

## Code map (new and touched)

New package `lib/kofin/downloads/` (shell code, strict mypy): `store.py` (the kofin.db `download` table), `manager.py` (service-side queue and workers), `files.py` (layout, naming, sanitization, free-space), `quality.py` (download device profiles and transcode URL construction, video and music). New module `lib/kofin/sync/kodidb/downloads.py` (strict, beside the other kodidb writers): the repoint and restore SQL for MyVideos and MyMusic, explicit column lists like everything else in that directory. Touched: `core/ipc.py` (three new guarded messages), `core/http.py` (a streaming request method), `core/api.py` (download/subtitle URL helpers), `plugin/context.py` and `plugin/router.py` (menu entries and routes), `service/main.py` (manager lifecycle), `sync/views.py` (Downloads node, NODE_LAYOUT bump), `sync/writers/movies.py` and `sync/writers/tvshows.py` (tag injection at the favorites-injection point), `sync/db.py` (DDL), `resources/settings.xml` + `strings.po` (Downloads settings block). Phase 2 adds `downloads/pending.py` and touches `core/state.py` (honest online flag), `service/kodiuserdata.py`, `service/player.py`, `plugin/play.py`, `plugin/context.py`. Phase 3 adds the music leg to `quality.py`/`files.py`/`kodidb/downloads.py` and touches `sync/playlists.py` (prune exemption for the Downloaded-music playlist).

## Storage decisions (fixed now, so every phase writes the same rows)

`kofin.db` gains one table in phase 1: `download(jellyfin_id TEXT PRIMARY KEY, media_type TEXT, series_id TEXT, state TEXT, origin TEXT, rel_path TEXT, container TEXT, size_expected INTEGER, size_actual INTEGER, quality TEXT, bytes_done INTEGER, userdata_json TEXT, queued_at INTEGER, done_at INTEGER, error TEXT)`. `state` ∈ queued|active|done|failed; rows leave the table only on remove. `series_id` is denormalized so the tvshow tag injection is one indexed lookup (does this show have any done download). `origin` is `user` or `auto:<seriesId>` (phase 4) — deletion safety and Finamp's "why is this here" question answered in one column. `quality` records the request that produced the file (`original` or a codec/bitrate/resolution string); nothing acts on it in phase 1 beyond display — it exists so a later needs-redownload feature is a diff, not a guess. `userdata_json` snapshots the server's UserData at queue time for phase 2's conflict rule. Paths are stored **relative** to the downloads root (Finamp's lesson: the root is a setting and may move; `rel_path` survives it). Phase 2 adds `pending_userdata(id INTEGER PRIMARY KEY, jellyfin_id TEXT, media_type TEXT, played INTEGER, position_ticks INTEGER, favorite INTEGER, event_at INTEGER, server_snapshot TEXT)` — NULL columns mean "unchanged".

File layout under the user's downloads root, human-readable from day one, names frozen at download time: `Movies/<Title (Year)>/<server original filename>`, `TV/<Show>/Season NN/<server original filename>`, `Music/<AlbumArtist>/<Album>/<server original filename>` (phase 3; transcoded files swap the extension for the real container). The server filename comes from `Content-Disposition` (V1); transcodes synthesize `<Title (Year)>.mp4` / `<NN Title>.ogg`. Sanitization strips FAT/exFAT-unsafe characters and trailing dots/spaces; a directory-name collision (two titles sanitizing identically) appends the first 8 chars of the jellyfin id — deterministic, applied only on actual collision. Files land as `<name>.part` and are renamed only after verification; a `.part` at startup is a resume candidate (originals) or deleted (transcodes).

## Phase 1 — originals, repoint, node, manager

**W1.1 — settings and strings.** New level-0 "Downloads" category: `downloadsEnabled` (bool, default false — the whole feature is opt-in), `downloadsPath` (path type, default `special://profile/addon_data/plugin.video.kofin/downloads/`), `downloadsMaxParallel` (spinner 1–4, default 2). Constraint check: no `<dependencies>` on any `list[string]` (the Omega unregister bug); these are bool/path/spinner so plain `visible` dependencies on `downloadsEnabled` are safe. `SettingsApplier` gets a `downloadsPath` hook that write-probes the new root and toasts on failure at apply time, not at first download. New string ids from the next free 30xxx block; full Kodi restart needed before live-testing them (string cache).

**W1.2 — `Http.stream` (core/http.py).** A streaming GET: yields chunks (256 KiB), takes the same headers/timeout/abort plumbing as `request`, supports a `Range` start offset, maps 416 to "already complete" (jellyfin-android's convention, V1), keeps the module Kodi-import-free, and consults the abort predicate **between chunks** — the read timeout (30 s) bounds a dead socket, the predicate bounds a stopping service, and both matter at multi-GB sizes (the thread-stop doctrine, now with `_abort_transport` hearing `abortRequested`). No internal retry ladder: the manager owns retries. Unit tests with a fake session: chunk iteration, range resume, 416-complete, abort mid-stream raising `ServerUnreachable`.

**W1.3 — `downloads/store.py` + DDL.** The `download` table (above) in `sync/db.py kofin_tables`, CRUD in `store.py`, all through the existing `Database("kofin")` plumbing — the writers' connection can read it (W1.8) because it is the same file. States move queued→active→done/failed; `bytes_done` updated per chunk-batch so a restart resumes originals with `Range`.

**W1.4 — `downloads/files.py`.** Layout/naming per the storage decisions, sanitization vectors as table-driven tests (unicode kept, punctuation policy explicit, the collision suffix), free-space precheck (`os.statvfs` on the root: refuse a queue-add when `free < expected + 2 GiB` — Emby's reserve), and >4 GiB warning when the filesystem is FAT32.

**W1.5 — `downloads/manager.py` + service lifecycle.** A manager owned by the service: worker pool of `downloadsMaxParallel` threads named `kofin-downloads-N`, each with its own `_new_api()` session (abort-predicated), draining queued rows oldest-first, single-flight per item. Per item: fetch to `.part` via `Http.stream` (originals: `/Items/{id}/Download`, V1), verify `size_actual == Content-Length`, download external-subtitle sidecars (W1.6), rename, repoint (W1.7), stamp the tag (W1.9), fire `refresh_libraries` — command paths own their refresh; never a blanket one (widget-refresh doctrine). Retry with the manager's own backoff (3 attempts, then state=failed with `error`); resume from `bytes_done` on retry and restart. Lifecycle: built in `Service._connect` when `downloadsEnabled` (like the library manager: degrade, don't die), stopped in `_shutdown` after the library join with bounded joins; a mid-chunk stop request must exit within one chunk + one read timeout, and the live gate measures it. IPC: `DOWNLOAD_ADD`, `DOWNLOAD_CANCEL`, `DOWNLOAD_REMOVE` declared in `core/ipc.py`'s closed-world registry, all guarded (REMOVE deletes files; the other two are guarded for uniformity with the library commands). Progress surface in phase 1 is deliberately minimal: a toast on queue/complete/fail and log lines — no new window properties (`core/state.py` additions must argue their way in; a skin progress channel can argue later).

**W1.6 — external subtitle sidecars.** An original download does not contain the external subtitles the streaming play route attaches (`plugin/subtitles.py`), so a repointed item would silently lose them. For each external subtitle stream in the item's MediaSource: fetch `/Videos/{id}/{sourceId}/Subtitles/{index}/Stream.{ext}` (`subrip`→`srt` mapping, from the downloader-repo prior art) and save beside the media file as `<basename>.<lang>.<ext>` — Kodi auto-loads sidecars by name, which also keeps them for any other app reading the tree. Embedded subtitles ride along in the original container by definition; transcodes (phase 3) carry none, matching streaming behavior.

**W1.7 — the repoint (`sync/kodidb/downloads.py`).** The full Emby shape, proven mandatory by V5: get-or-create path rows for the target directories, repoint `files.idPath`, set `files.strFilename` to the basename, update the media-table path-mirror columns (movie basePath/parent-path columns and their episode equivalents — enumerate against the schema fixtures, not from memory), and stamp the new path rows the way the writers stamp their plugin path rows — for episodes that includes the show/season directory rows carrying `strContent='tvshows'`, `metadata.local` and `useFolderNames=1`, because the info dialog resolves a scraper for the item's path and loses cast/tags without it (the CLAUDE.md constraint; Emby's `get_add_path` does exactly this). `idFile` never changes — bookmarks and playcounts stay attached (V4). Restore is not a stored backup: the writers construct plugin paths deterministically from the jellyfin id, so remove-download re-runs the writer's own path stamping (`update_path` with the writer-built values) and deletes now-orphaned downloads path rows. Art stays on server URLs in phase 1 (cached art renders offline, V7; localizing art is phase 4's export toggle).

**W1.8 — writer tag injection.** `Kofin Downloads` is a tag, and tags are replaced wholesale on every writer pass, so out-of-band tags die on the next sync (the favorites precedent proves the fix): movies append the tag in `writers/movies.py` at the same point `Favorite movies` is appended, gated on a `download` row in state done; `writers/tvshows.py` likewise tags a show when `EXISTS(download WHERE series_id=? AND state='done')`. This touches transplant code exactly as far as the favorites injection already does — an appended tag before `add_tags`, driven by a lookup on the same kofin.db connection the writers already hold — and no further. L2 cases pin it (see Tests).

**W1.9 — immediate tag flip + Downloads node.** The manager stamps/removes the tag directly through the kodidb tag helpers at complete/remove time (the writer injection covers resyncs; the manager covers *now*), removing a show's tag only when its last downloaded episode goes. `sync/views.py` generates a Downloads folder (movies + tvshows nodes filtering `tag is "Kofin Downloads"`) when `downloadsEnabled`; `NODE_LAYOUT` bumps so existing installs regenerate; node labels are written as text, never bare 30xxx numbers (the FilterLabel constraint).

**W1.10 — context menu and routes.** `_manage_options` gains Download / Cancel download / Remove download, gated on: `downloadsEnabled`, item type (Movie, Episode, Season, Series in phase 1), the server's `CanDownload` on the fetched item (same two-gate pattern as delete's `CanDelete` — never offer what the server will 403), and the store's state for the item. Remove confirms with a yes/no naming the item (context scripts may dialog; the no-modal constraint binds node `<path>` routes, not RunPlugin handlers). Season/Series expand client-side through the existing paged `downloader` machinery (the server has no folder download — V1/server source), show a count + total size confirm (MediaSources rides the listing fields), and enqueue per-episode rows. Routes `download`/`canceldownload`/`removedownload` fire the guarded IPC and exit.

**Phase 1 non-goals, stated so they are decisions rather than omissions:** no multi-version selection (the default MediaSource is downloaded; versions keep streaming), no boxset expansion, no pause/reorder UI, no bandwidth limiting or WiFi-only (Kodi exposes no metered-network signal), no art localization, no automatic re-download on quality-setting changes (recorded in `quality`, acted on never), no play-route changes at all — a repointed item never reaches the plugin, which is the point (V4).

## Phase 2 — offline correctness

**W2.1 — an honest online flag.** `state.set_online(False)` gains callers: the websocket's `on_disconnected`, and a `_connect` probe failure when the flag is currently up (one edge, no flapping: the probe only runs while `_online` is false in today's service, so the disconnect callback is the primary lowering edge and the probe the raising one — the wake-time FastSync stays untouched and unconditional). Before wiring, audit the six existing `is_online` consumers (`shims.py:82`, `library.py:408/583/2002`, `plugin/syncplay.py:42`, `adduser.py:179`) against honest semantics; the latch-true behavior is *documented as load-bearing* in `library.py`'s resume comment, so that path's polling must be re-verified under the new semantics (it polls regardless — the flag only gates a skip — but the audit is the work item, not an assumption).

**W2.2 — fast failure on the play route.** `plugin/play.py`: when the item resolves through kofin.db to a row with no done download and `state.is_online()` is false, fail inside the first second with a dedicated "not available offline" toast — before any transport is built. V8's baseline is ~8 s of spinner into a generic error; the target is <2 s including interpreter start. Downloaded items never hit this (they never reach the plugin).

**W2.3 — offline manage().** `manage()` currently opens with a server fetch and dies offline in a toast (feasibility, context.py). Offline, build the menu from local state alone: Remove download (store lookup), Settings — no watched/favorite/delete entries, since those are server writes phase 2 queues only for *playback*-driven events, not menu actions (a menu action failing loudly is honest; a playback event vanishing is not).

**W2.4 — the pending-userdata queue.** `downloads/pending.py` + the `pending_userdata` table. Producers: `service/kodiuserdata.py` — on `ServerUnreachable` (or short-circuit when offline: skip the doomed 6 s attempt, V6) enqueue the played/resume delta instead of dropping it; `service/player.py` — a failed stop report enqueues the final position. Replay: in `_run_post_connect`, after capabilities and **before** `_catch_up_after_reconnect`'s FastSync, drain oldest-first — position+played travel in one `POST /Items/{id}/UserData` (the documented-routes rule; one call avoids Findroid's played+stale-position ghost), favorites through the existing verbs. Conflict rule, better than the field standard and cheap: fetch the item's current UserData; if the server's `LastPlayedDate` moved past the row's `server_snapshot`, someone watched elsewhere while we were offline — keep whichever position is further and drop the rest of the delta; otherwise replay as-is. The echo that comes back terminates like every userdata echo (announcement-free SQLite writes).

**W2.5 — service probe cadence while offline.** Already fixed ahead of this plan (PR #110): the probe is single-attempt on `PROBE_TIMEOUT` and every service transport hears `abortRequested`. Phase 2 only re-verifies both under its live gates.

## Phase 3 — transcodes and music

**W3.1 — `downloads/quality.py`, video.** A download device profile forcing transcode at the downloads bitrate/resolution with `Protocol: "http"`, `Container: "mp4"` — the server muxes progressive mp4 as fMP4 (`EncodingHelper.cs:7615`), which is seekable on disk even unfinalized and carries AV1 (V3 amended; measured ~0% container overhead vs ts's +5%). Flow: PlaybackInfo → `TranscodingUrl` with `master.m3u8`→`stream` rewritten (Streamyfin's rewrite) → stream to `.part`. `deviceId` + `PlaySessionId` ride the URL; cancel and failure fire `DELETE /Videos/ActiveEncodings` (connection close also kills the job, but saying so is free). Transcodes are not Range-resumable — restart on failure, delete stale `.part`s. **Concurrent transcode downloads cap at 1** regardless of `downloadsMaxParallel`: the encoder runs flat-out with throttling force-disabled (V2), and two parallel pulls would saturate the server unbidden. Completion: clean EOF + a duration probe against the item's runtime (no Content-Length exists). Settings: `downloadsVideoQuality` (Original default / bitrate list reusing the transcode-tab vocabulary), sharing `preferredVideoCodec`/`preferredAudioCodec`/`maxResolution`; AV1 works when the server has an encoder for it, at encoder-bound speed.

**W3.2 — music downloads.** Types Audio/MusicAlbum/MusicArtist/Playlist join the context gates; containers expand client-side to tracks. Originals via `/Items/{id}/Download`; transcodes via the same PlaybackInfo flow — the music transcoding profile is already plain-http progressive, no rewrite caveats, and Ogg/Opus on disk is complete as-is. Settings: `downloadsMusicQuality` (Original / Transcode), `downloadsMusicCodec` (default opus), `downloadsMusicBitrate` (default 128) — mirroring the streaming music tab's spinner style. The song repoint updates the per-song path row + `strFileName` with the **downloaded container's extension** (the musicdb extension rule; V4 proved the repoint in both path modes), and restore re-runs `get_song_path_filename`'s own construction. Build-time checks recorded in the feasibility doc: FLAC tags → Vorbis comments on 10.11, and embedded art is expected not to survive (Kodi renders from its own DB; `folder.jpg` export is phase 4).

**W3.3 — the Downloaded-music view.** Repointed songs' paths live under the downloads root, so a smart playlist with a path-starts-with rule is a real "Downloaded music" view with no schema tricks. It lives in the `Kofin/` playlists folder, so `sync/playlists.py`'s pruner must except it by name exactly as it excepts the folder icon — otherwise it survives one poll (the documented pruner behavior). The rule's path value regenerates when `downloadsPath` changes (a `SettingsApplier` hook, same as W1.1's probe).

## Phase 4 — auto-next, retention, export

**W4.1 — auto-download next episode.** A player-progress hook: when a *downloaded* episode crosses 80%, and `downloadsAutoNext` is on, resolve the next unwatched episode (`api.adjacent_episodes` / NextUp) and enqueue it with `origin='auto:<seriesId>'` at the same quality. Keep-ahead bounded by `downloadsAutoNextKeep` (default 2). No client in the ecosystem ships this; the design is deliberately boring — a hook, a lookup, an enqueue.

**W4.2 — retention.** A manager sweep deletes **auto-origin** episodes once watched and older than the keep window; user-origin downloads are never auto-deleted. Every deletion goes through the full remove path (restore, untag, refresh) — never a bare file unlink.

**W4.3 — metadata export.** `downloadsExportMetadata` (default off): NFO **with uniqueids** (the downloader-repo NFOs omit them and are a dead end), `poster.jpg`/`fanart.jpg`, music `folder.jpg`, written into the media tree beside the files (decision recorded in the feasibility doc). Exported at download time, freshened never — the export is an escape hatch for other apps, not a mirror.

## Tests

L1 units per new module as listed in the work items; the ones worth calling out: `Http.stream` abort/resume/416 semantics, the sanitization vector table, manage-option gating (enabled × type × CanDownload × store-state matrix), the m3u8→stream rewrite, and the phase-2 replay conflict rule (server-moved / server-unmoved / favorite-only cases). L2, on the pristine schema fixtures and parameterized over every gated schema like `test_sync_writers.py`: full sync → repoint → **dump-level assertions** on the path-row stamps and mirror columns; repoint → restore → **byte-identical dump** (the house invariant is the enforcement mechanism for W1.7's column list); writer rewrite of a downloaded item keeps the tag, and of a removed one drops it; zero-orphan removal with download rows present; music repoint through `music_dump()` (the `DATETIME('now')` triggers). The `download` DDL joins `test_sync_schema.py`'s ambit only if it gains keyed constants — it should not.

## Live gates

Phase 1: G1 download a movie and a season (count+size confirm) from the context menu on the local Omega box and the Piers Bravia; G2 blackhole the server (the feasibility method), browse the Downloads node, play both items, resume both (V4 protocol); G3 info dialog on a repointed episode still shows cast/director (the path-stamp constraint, live); G4 `UpdateLibrary` resync keeps the tag; G5 remove-download restores streaming playback and a byte-identical mapping (spot-checked rows); G6 cancel mid-download and quit-Kodi mid-download — service exit bounded (one chunk + read timeout), `.part` handled on restart; G7 downloads to an SD-card path on the Bravia (the Android storage claim, unverified in the study). Phase 2: G8 offline watched/resume events replay on reconnect and survive a competing server-side watch (conflict rule, both branches); G9 non-downloaded play fails <2 s with the dedicated toast; G10 offline manage() offers Remove. Phase 3: G11 fMP4 transcode download seeks and resumes (V3 protocol) at both spinner qualities; G12 Opus album download plays from musicdb, tags intact, Downloaded-music playlist lists it, prune leaves it alone. Phase 4: G13 a three-episode auto-next chain with retention deleting the watched head; G14 exported tree scans clean in a bare Kodi profile with the local-info scraper.

## Phase 1 live-gate results (local Omega, 2026-08-08)

G1 movie and season downloads from the context menu: pass, after a fix. The season landed its four episodes in **three** directories — the collision suffix asked "does another download live under this directory", which is true of every sibling in a season. Directories belong to owners (a film, a show), not items; `files.item_dirs` now returns (owning directory, leaf) and uniqueness runs on the owner. G2 offline (server blackholed, cold boot): Downloads nodes render in 21 ms with cached posters, a downloaded episode reads LOCAL beside streaming siblings, the movie played, seeked, wrote its bookmark (1325 s) and resumed at 22:11, and a repointed episode played too. G3 info dialog on a repointed episode: full cast with actor images, plot, writer, studio, rating — the path stamps hold. (First attempt proved nothing: the UFC episodes have no cast on the server at all, so the check was redone against an Archer episode with 24 cast entries.) G4 resync: a **Repair** of the Shows library — the most destructive resync there is — recreated every episode row with new Kodi ids (17483+) and the writers' `reassert_on` re-pointed each one inside the writer pass; tag followed the show to its new id. G5 remove: files deleted, path rows pruned, every file row back on its plugin URL, show tag dropped while the movie's stayed. G6a cancel mid-transfer: `.part` deleted, row gone — but the empty season directory survived, now pruned. G6b quit mid-download: Kodi exited in 3 s with a 200 MB transfer in flight, no watchdog warnings — but the row settled *failed* and nothing resumed it, contradicting this plan's own contract; a stop now leaves the row active for `recover_interrupted`, verified live resuming by append (247 MB → 448 MB → 1128 MB). G7 (Android SD) is the Bravia's gate and is still outstanding.

Left as designed, noted for phase 2: the Downloaded-shows node lists the whole show (Kodi tags shows, not episodes), so drilling in shows every episode with only some local. And the plan's own note stands — the first attempt to time an offline miss was invalid, so V8's ~8 s remains the baseline the phase-2 fast-fail has to beat.

**W2.7 — the downloaded badge, in native library lists.** The Downloads nodes answer "show me only what I have"; the badge answers "which of these do I have?" while browsing Movies and TV shows normally, and the two are complementary rather than alternatives. Kodi's own overlay is unavailable for it: `ListItem.Overlay` is a closed seven-value enum (`GUIListItem.h`) written by core from playcount at seven sites in `VideoDatabase.cpp`, so an addon can neither extend it nor set it on a library row. What *is* open is art — `CVideoDatabase::GetArtForItem` selects every `type,url` for an item with no whitelist, and `ListItem.Art(<anything>)` returns it (`GUIInfoManager.cpp:11349` → `item->GetArt`), verified live on a real library row. So the signal is one art row per downloaded item, type `kofin.downloaded`, pointing at an addon-shipped 32×32 badge; the manager stamps it on completion and clears it on removal, and the writers' `reassert_on` re-publishes it (a repair rebuilds the item under a new Kodi id and its art goes with the old one). Unlike the tag it needs no injection into a writer's replace-the-set list: `artwork.add` only touches the types it knows and only the *removal* path clears art wholesale — which is correct, since an item that left the library should take its badge with it. The L2 suite pins survival across a resync and zero trace (art rows included) after removal.

An episode badges its **season and its show** as well as itself, so browsing a show the ordinary way — show, then seasons, then episodes — says at every level which parts are held offline; a show can have twenty seasons, and without the middle level the viewer opens each one to find out. That is also what makes the Downloaded-shows node's full listing a feature rather than a compromise: it lists the whole show deliberately, and the badges mark what is there. Removal *recomputes* the ancestors from what survives rather than decrementing them — a season keeps its badge while any episode in it remains, and a counter that drifted once would be wrong forever.

The badge deliberately says only "downloaded". Pairing it with watched state belongs to the skin, exactly as `ListItem.HasVideoVersions` is paired there today — that infolabel is itself only a boolean, computed in `movie_view`'s SQL, with contuary choosing `overlays/versions.png` from it. Making the art *url* depend on playcount would mean rewriting the row on every playback and every userdata echo, and a missed rewrite is a badge that lies. Two icons ship (`resources/media/downloaded.png`, `downloaded-watched.png`) so a skin needs no assets of its own; contuary's first-match-wins overlay variable takes them as two lines above its `$INFO[ListItem.Overlay]` fallback.

## Phase 2 live-gate results (local Omega, 2026-08-08)

G9 fast fail: a non-downloaded item offline is refused in **0.1 s** against V8's ~8 s baseline, with a named toast; no transport is built. G10 offline actions: the Jellyfin actions menu offers exactly Remove download and Settings. G8 replay, end to end: an episode watched to the end offline parked `played=1`, the server read `Played: False` before the reconnect and `Played: True` after it, the row cleared, and Kodi's own state survived the catch-up that followed. The conflict rule was then tested against the real server with a genuine conflict — a stale local position of 2 minutes replayed against an account that had reached 8 minutes elsewhere — and kept the further position (4800000000 ticks), which is the case every shipped Jellyfin client gets wrong. The Downloaded-episodes node ships and lists exactly the downloaded episodes across shows.

One fix came out of these gates, and it was the common case rather than an edge: the flag only stated an outage via `_go_offline`, which is reachable only from a *previously online* service, so a device booted away from its server left the flag absent and every refusal went back to waiting for the transport. A failed probe now states the outage whether or not we were ever online.

## Sequencing notes

W1.2/W1.3/W1.4 are independent and first; W1.7 is the riskiest item and gets its L2 suite before the manager exists (repoint a hand-inserted row); W1.5 assembles the rest. The feasibility doc and this plan should land together at the head of `feat/downloads-p1`. The `Kofin Downloads` tag name, node labels, and settings ids above are final unless the user objects — changing any of them after phase 1 ships means a migration, so objections are cheapest now.
