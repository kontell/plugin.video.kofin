# Phase 3 — native movies through public Kodi APIs

Implemented 2026-10-07 on `feat/or-phase3-movies`. The internal API build now synchronizes selected movie/mixed libraries into Kodi's native movie library. The release version remains reserved at `0.90.0`; the public prerelease has not been published. The P1D Piers Flatpak satisfies the approved target requirement; the phase 3 release exit still requires development-repository delivery.

## Implementation

`sync/backends/api/library.py` owns one serialized movie worker. It fetches all selected movie listings before publishing their union, validates page totals and identities, and retains the last complete snapshot on failure. Websocket changes, complete enumeration, explicit removals and repair feed private desired/applied generations. Kodi receives immutable snapshot directories, never an interactive browser result or a partially fetched page.

`store.py` keeps generations, pinned scanner snapshots, native identity caches, expected userdata and durable local edits in Kofin's own SQLite file. A stable server/user namespace and item query URL survive library movement and native-ID replacement. Operations remain pending until public readback confirms their outcome; stale acknowledgements cannot complete newer work. A pending local edit is delivered idempotently before an older server snapshot can overwrite it.

`provider.py`, `metadata.py` and `movies.py` implement scanner listing, `refresh_info`, tombstone-aware `check_exists`, local-metadata source binding, scanning, scalar patches, cast/stream refresh, watched/resume restoration and source teardown. Every native mutation validates both the namespaced unique ID and exact resolver URL. Repair re-resolves replaced IDs. Metadata removals clear keys previously supplied by Kofin and preserve unrelated tags, IDs, ratings and artwork. Kodi controls defaults and fields absent from its public interface; exact stream-flag/authority parity remains open in the ledger.

The service starts native replay independently of server reconnection, then polls and consumes server events. Library settings expose movie/mixed selection; update and repair routes dispatch to the API worker. Native playback and context actions use validated public mappings. Dynamic browsing retains the existing live-server routes and lightweight ListItems. Native TV, music videos, music, collections, downloads and legacy SQL maintenance remain unavailable.

Normal startup requires compatible public capabilities, compatible private backend state and an initially empty video/music library. The private setup marker binds native work to one server/user namespace. The build does not adopt old SQL mappings, clear a user's existing library or silently switch namespaces. Dynamic browsing remains available when native setup is blocked. Use a fresh Kodi profile for a real transition.

## Installed-service follow-up — 8 October

The user's normal installation exposed a missed startup gate: the capability checker rejected the approved Flatpak solely because its revision included `dirty`, so selecting a library never started a worker. The original isolated scanner fixture did not exercise that path. Build provenance is now diagnostic only; the required interface and private-state checks remain enforced. A service regression uses the recorded P1D capabilities through the real capability probe and verifies that selecting movies starts the worker without an override.

Once started, the real catalogue exposed Kodi metadata normalization: InfoTag setters trim ASCII whitespace, movie arrays round-trip through the configured separator, and a full premiere date determines the movie's public year. Exact comparison against the original server sort titles, tags, combined studio names and conflicting production years left valid writes pending. The mapper now uses Kodi's persisted representation, discovers the configured separator once per worker through the public InfoTag API, and retains the original DTO privately. Regressions cover trimming, tags, combined studios, a custom separator and conflicting release years. Readback still rejects genuinely different metadata.

The fixes were applied to the installed addon with the original files backed up, preserving its selected library, credentials and profile. Normal service startup then imported the selected content and completed every published operation with status **Done** and no pending work. A subsequently selected larger catalogue also completed with no pending operations, including recovery when the initial scanner exceeded its bounded wait. The status now changes to Updating media while native work is being applied. [Sanitized installed-startup evidence](installed-startup.json) omits catalogue titles, identities and counts. This verifies the normal service and real Jellyfin path in addition to the earlier synthetic fixtures.

The kodi-drive contribution check found that the default-icon and missing-lastplayed behavior encountered here are directly explained by Kodi source; no duplicate skill was added. Source references: [`FillInDefaultIcon`](https://github.com/xbmc/xbmc/blob/e513e0ff/xbmc/utils/ArtUtils.cpp), [`CVideoDatabase::SetPlayCount`](https://github.com/xbmc/xbmc/blob/e513e0ff/xbmc/video/VideoDatabase.cpp). ## PR review follow-up — 8 October

Failed queued events and local userdata delivery now leave scheduled full enumeration runnable. Retries preserve an earlier recovery deadline, and one failed command does not prevent later commands from running. Regression scenarios cover a permanently unavailable item, an event before the first snapshot and failed local delivery. Resume echoes use the same less-than-one-second position tolerance as native readback, retaining expiry and generation checks. Play Next requires an imported mapping and tolerates private-store lookup failures. The live fixture's media-generation subprocess now has a timeout.

Pagination now requests supported `DateCreated,SortName` ordering with matching ascending directions. `Id` is not an [`ItemSortBy`](https://github.com/jellyfin/jellyfin/blob/v10.11.0/Jellyfin.Data/Enums/ItemSortBy.cs) value; the server's collection model binder silently discards it. Read-only checks against the P1D installation's configured Jellyfin 12.2.0 server confirmed repeatable first-page ordering and disjoint adjacent pages. These checks sample a stable catalogue; they do not prove snapshot isolation during concurrent server edits.

The reported fieldless single-item metadata loss was not reproduced. [`UserLibraryController.GetItem`](https://github.com/jellyfin/jellyfin/blob/v10.11.0/Jellyfin.Api/Controllers/UserLibraryController.cs) constructs [`DtoOptions`](https://github.com/jellyfin/jellyfin/blob/v10.11.0/MediaBrowser.Controller/Dto/DtoOptions.cs) with all fields enabled; that endpoint has no `Fields` parameter. All eight disputed fields were present and matched the full listing response for three live movies. The endpoint remains unchanged, with its contract documented and incremental/local-ack preservation tested. [Sanitized live review evidence](pr-review.json) contains only version information and boolean results. These review checks did not change the installed addon or the user's library. The source explains the findings directly, so the kodi-drive contribution check calls for source links rather than a duplicate skill.

## Installed-use follow-up — 8 October, evening

A day of ordinary use on the installed Flatpak build — Kodi's own Clean Library with the add-on disabled, then deselecting and re-selecting the movie library — exposed four defects, each diagnosed from the Flatpak's `kodi.log` and its databases and fixed on this branch.

**Whole-library removal was quadratic.** Every tombstone ran `VideoLibrary.RemoveMovie` and then a full `VideoLibrary.GetMovies` readback of the whole directory to confirm it, so removing the installed catalogue took about thirty minutes, one movie at a time. `Movies.remove` now applies tombstones as a batch: when no pinned record survives the removals, one `VideoLibrary.SetSourceContent` with `content: "none"` and `clearmode: "remove"` lets Kodi's `RemoveContentForPath` delete the directory whole; otherwise the rows go through `RemoveMovie` and one readback confirms every removal. `SetSourceContent` announces nothing where `RemoveMovie` notified per row, so the clear is followed by one `UpdateLibrary(video)` — the directory is unbound by then, so the scan walks nothing and only fires the library event the home widgets listen for. Only `"remove"` deletes scraped items — `"clear"` merely unbinds the scraper (`methods.json`, `VideoLibrary.SetSourceContent`), which is what the previous end-of-reconcile call sent. Measured on the P1D Flatpak: from the removal prompt's Yes to status Done in 59 s, 45 s of it inside Kodi's `RemoveContentForPath`, with no `RemoveMovie` call and no error.

**A deselection during enumeration was imported anyway.** `full_sync` read `librarySelection` once at entry; a library deselected while its pages were still downloading was published with the stale selection, scanned in full, and then removed again by the queued `RemoveLibrary`. The selection is re-read before publication and a library no longer selected is dropped; an emptied selection publishes nothing.

**The scan wait was sized for the fixtures.** `Movies.wait` had a fixed 60 s cap, and the installed catalogue scans at roughly 60–70 ms a movie, so every full import logged `TimeoutError: native movie operation did not converge` and recovered only through the retry's idle wait. The cap is now idle time: the deadline moves while `Library.IsScanningVideo` reports the scanner busy, so a running scan is never abandoned and a scan that stops without `onScanFinished` still times out 60 s after going idle. The installed catalogue's 126 s scan completed without an error line.

**Every imported movie sat in the in-progress widget until its detail patch.** The scanner ListItem was built through the browse-row path, which stamps `setResumePoint(0, total)` so a plugin listing masks the bookmark Kodi saved for the plugin path. On a scanner row Kodi persists any set point — `CBookmark::IsSet` is `totalTimeInSeconds > 0` — as a type-1 bookmark with `timeInSeconds = 0`, and the in-progress smart-playlist rule is that row's existence, not its time (`SmartPlayList.cpp`, `FieldInProgress`). The per-movie `SetMovieDetails` with `resume.position = 0.0` cleared each one (`UpdateResumePoint` treats 0.0 as `ClearBookMarksOfFile`), which is why the widget emptied itself minutes later. `metadata.build` now passes `stamp_zero_resume=False`; a scanner row carries a resume point only when the server holds a position. Measured on the P1D Flatpak across two imports: no `timeInSeconds = 0` bookmark at any sample during or after the scan, and the in-progress filter returned only the server's real positions throughout the detail pass.

**Home widgets stayed empty after the library was refilled.** With the library populated again, the only widget providers that refreshed were `addons://` ones: a `CDirectoryProvider` whose last fetch found nothing — every movie widget, right after the removal — is deaf to later library announcements, and the skin's widget sections bake their `Library.HasContent` gate at window load. The SQL backend answers this with a skin reload on the first-content transition (`sync/refresh.py`), a module the API distribution omits. `Library.apply` now compares `MovieStore.populated()` — any owned movie with a native row — before and after a reconcile, and an empty → populated transition owes one `ReloadSkin()`, fired after `Library.HasContent(Movies)` has flipped (10 s poll) and never while video plays; the worker tick flushes a held reload. A partly failed first import still owes it.

Regressions cover each change: whole-library removal through one clear with a fresh and with a stale pin, partial removal with one readback, an unconfirmed removal staying pending, a 300 s scan that completes against the idle cap and an idle scanner that still times out, a scanner ListItem with and without a server position, enumeration that drops a deselected library or publishes nothing when the selection emptied, and the first-content reload — once per transition, held during playback, and owed by a partly failed import. Raw evidence — screenshots and the sampled counts — stays under gitignored `tests/live/results/or-phase3/`; this section omits catalogue titles, identities and counts.
