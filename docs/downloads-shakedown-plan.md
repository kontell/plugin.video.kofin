# Downloads shakedown: plan

Eight changes to the offline-downloads feature, raised from live use after phase 4 landed. The feature's own design record is `docs/offline-downloads-plan.md` (W-numbered) and its evidence base `docs/offline-downloads-feasibility.md` (V-numbered); neither is restated here. Work items are D1–D8, one per raised point, and live gates are S-D1–S-D8. Decisions already taken with the user: the size report is a settings button sized from disk, not from the store; the folders that survive an individual delete are the three category folders (`Movies/`, `Shows/`, `Music/`), not the whole tree below them; a download subscription **mirrors** the server side — additions download, departures have their downloads removed.

## What the code says today

Three of the eight points are questions, and the code answers two of them outright.

**A downloaded playlist is not kept up to date, and nothing intends it to be.** `sync/playlists.py` materializes each Jellyfin music playlist as a `.m3u8` under `playlists/music/Kofin/` on the library poll (`full_sync.py:278`, `library.py:371`), and that is a one-way *listing* refresh: it rewrites track lines from MyMusic rows and never looks at the download store. `downloads/auto.py` has exactly one subscription — `downloadsEpisodeShows`, series only. So a playlist downloaded today is a snapshot of its membership at that moment, and a track added to it on the server is never fetched. D7 is what makes the answer yes.

**A toast per track is the album grouping working as written, on a request it was never shaped for.** `manager._announce_complete` collapses song completions by `group_id`, and `group_id` is `SeriesId or AlbumId` (`manager.py:598`) — the *item's* container, not the request's. Album and artist downloads therefore announce once per album, which is what the comment promises. A playlist of twelve tracks off twelve albums is twelve complete albums, so it announces twelve times. The unit the user chose has no representation in the store at all, which is what D6 adds.

**The music prompt after playback is a missing type gate, and the same gate exists twice already elsewhere.** `player.offer_remove_download` tests the settings, the id and `watched_to_end`, and never the type — where its sibling `offer_delete` gates on `DELETABLE_TYPES` ("A song or a music video reaching its end is not an invitation to delete anything"), `manager._retention_sweep` skips anything outside `store.VIDEO_MEDIA_TYPES`, and `manager._mark_watched` skips it for the same stated reason ("'watched' is not a thing a song is"). The end-of-playback offer is the one path of the three that never got the rule. D3 is a three-line fix with a test.

**Why an item watched on one profile vanished on another is not answerable from the code alone**, and the settings on the rig say it should not have happened. Two Kodi profiles share no database, no `kofin.db` and no downloads root (`kofin-test` → `~/kofin-downloads`, `kofin-jf12` → `~/jf12/kofin-downloads`, the master profile → its own `addon_data/…/downloads`); the only state they share is the *server*. That leaves three mechanisms, each with its own log line:

1. **A server-side delete.** `player.offer_delete` → `api.delete_item` removes the item from Jellyfin, and every other profile then loses its library row through the normal change feed. Logs `deleted <id> after watching`. Needs `enableDelete` **and** `deleteAfterWatching` **and** the server's `CanDelete`.
2. **A played push that arms the other profile's sweep.** Playback reporting (or `manager._push_played`, which fires whenever a download's file is found missing) marks the item played server-side; the other profile picks that up as `UserDataChanged`, writes playcount 1, and its own `_retention_sweep` — which reads Kodi's playcount, not the server's — removes *its* download of the same item. Logs `retention: removing watched <id>` on the second profile. Needs `downloadsDeleteAfterWatching` + `downloadsDeleteAutomatically` there.
3. **The stale sweep.** `_stale_sweep` collects watched items past `downloadsStaleDays` and is deliberately not nested under the watched toggle. Logs `stale:` on the second profile. Needs `downloadsDeleteStale`.

**Ruled out: the exported NFO as the carrier.** Proposed and checked 2026-09-01 — that kofin's metadata export writes a watched state, another profile flips it in the file, and the first profile reads it back. Every link is absent. `export.movie_nfo`/`episode_nfo`/`tvshow_nfo` write title, year, premiered/aired, plot and uniqueids and nothing else; the real file on the rig (`…/downloads/Movies/Indian Summer (1972)/Indian Summer.nfo`) carries no `playcount`, `lastplayed` or `watched`, and the module is write-once by design ("an escape hatch, not a mirror… freshened never"). Nothing in kofin reads an NFO back — the only `.nfo` references outside `export.py` are a comment in `fields.py` and the pruning companion set in `manager.py`. Kodi's own scanner *does* read `playcount`/`lastplayed` from an NFO, but that needs the downloads root to be a video source and no profile's `sources.xml` names one. And the three profiles do not share a downloads folder in the first place, so there is no file for one to write and another to read. Kept here because the mechanism is real in general — an NFO carrying watched state, scanned, does set it — and because the check it suggests is worth keeping: a profile that ever *had* the downloads root as a video source would hold Kodi-scanned duplicate rows built from those NFOs, which S-D4 rules out while it is there.

None of `enableDelete`, `deleteAfterWatching`, `downloadsDeleteAfterWatching`, `downloadsDeleteAutomatically` or `downloadsDeleteStale` is set on any of the three kofin profiles on P1D as of 2026-09-01 (they hold their `false` defaults — only non-default values are written to `settings.xml`), and neither `kodi.log` nor `kodi.old.log` holds any of the three lines. So the event predates the current logs or happened on another device. **D4 is an investigation, not a change**, and it runs first because mechanism 2 would mean the fix is not in `player.py` at all.

## D1 — a download size report

A new `downloadsShowSize` action button immediately above `downloadsDeleteAll` in the Downloads category, `RunPlugin(plugin://plugin.video.kofin/?mode=downloadsize)`, no `<close>` — the same shape as "Manage shows" and "Delete all downloads", so the report reads as a sub-dialog of settings and answering it returns there.

New module `downloads/usage.py`: `scan(root)` walks the root with `os.scandir` and returns per-category bytes and file counts keyed by the three names `files.py` owns (`MOVIES_DIR`, `SHOWS_DIR`, `MUSIC_DIR`), plus an `Other` bucket for anything else under a root the user may be sharing with other media — the bucket is the honest half of the "the root is user-configurable" rule the deletion paths already respect. Sizes come from `DirEntry.stat().st_size`, so sidecars, NFOs, art and abandoned `.part` files are all counted; that is the whole reason for walking the disk rather than summing `size_actual`, which under-reports by everything the store never knew about. `files.free_bytes(root)` supplies the free-space line (it already answers -1 for "could not tell", which must render as "unknown", never as 0).

Presented with `xbmcgui.Dialog().select` over `ListItem(label, label2)` rows — label2 is where every skin puts a right-hand value, which is what makes the column line up without a monospace assumption. Selection is a no-op; the dialog exists to be read. The walk happens in the plugin process, which must stay thin: a `DialogProgressBG` covers a root on slow or network storage, and the walk is bounded by an entry cap after which the dialog says so rather than hanging.

Two things the implementation added. The row list is built by a pure `actions.size_rows(report)` and only then wrapped in ListItems: Kodistubs' `ListItem` does not read its own label back, so a test that asserted on the widget could assert nothing — and the interesting part was never the widget. And `_human_size` grew a `_report_size` sibling rather than being shared as-is: its `max(1, …)` floor is right for the confirm dialogs, where "0 MB" would read as "this costs nothing", and wrong here, where a category nothing has been downloaded into is a real zero and "1 MB" is simply false.

Row labels reuse Kodi's own strings — `#342` Movies, `#20343` TV shows, `#2` Music, `#20161` Total, `#160` Free — which are already translated in every locale Kodi ships. That leaves five new kofin ids (30832–30836: the button label, its help, the foreign-files row, the empty-folder message and the capped-walk notice) rather than the ten a full set would have cost.

Rejected, and why: **sizing from `SUM(size_actual)`** is instant and works on removable storage that is not mounted, but it cannot see a sidecar, an exported NFO or an orphan, so its total is smaller than the disk's and a user reconciling the two would find kofin wrong. **A size in the Downloads node label** puts the number where the downloads are, but Kodi rebuilds that listing constantly and the walk would run with it.

## D2 — the category folders survive an individual delete

`manager._prune_empty_dirs(directory, root)` walks up removing empty directories and stops one level *below* the root, so the last movie deleted takes `Movies/` with it. The floor moves down one: `delete_media_files` already knows the row's `rel_path`, whose first segment is the category, so the stop becomes `<root>/<category>` and the per-title, per-show, per-season, per-artist and per-album directories inside it prune exactly as they do now.

The two bulk paths then take the category directories themselves, and only those: a new `sweep_category_dirs(root)` removes `Movies/`, `Shows/` and `Music/` when empty, by name, and never the root and never a sibling — the same name-gating doctrine that guards the generated node tree. Called at the end of `manager._apply_remove_all` and of `clean.remove_downloads`, after the per-row deletes, both of which already iterate to completion before they report.

Nothing creates the category folders eagerly: they appear with the first download of their kind and survive from then on, which is what "should stay" asks for without inventing empty folders on a profile that has never downloaded anything.

## D3 — no delete prompt for music

`player.offer_remove_download` gains the type gate its siblings have, on the item's Jellyfin type against `DELETABLE_TYPES` — the constant `offer_delete` already uses, in the module that already owns it. **Amended during implementation**: the plan said to test the *row's* `media_type` against `store.VIDEO_MEDIA_TYPES`, on the argument that it would make all three paths agree by construction. It would also have broken the prompt for video, because a row's `media_type` is `""` whenever the queue could not know the type up front (`submit` leaves it unknown until `record_details` learns it the slow way), and every existing test builds rows without one. The item dict is the vocabulary this method is handed and it always carries `Type`; the row's spelling stays where the sweeps use it. `_stale_sweep` is deliberately untouched: it removes music by design and it never prompts.

## D4 — the cross-profile deletion

An investigation with three named candidates (above) and no code change until one is confirmed. Run first: if mechanism 2 is the answer, the surprise is that Kodi's *local* playcount on profile B is written from profile A's server-side played flag, and the question becomes whether a download's retention sweep should trust a playcount it did not see earned — which is a different change from anything else here.

## D5 — artist art and NFO for music downloads

`export._export_song` writes one file: `folder.jpg` in the album directory. It gets three more, all best-effort and all written once when absent, exactly as the episode leg treats `tvshow.nfo`:

* `album.nfo` beside the tracks — `<album>` with title, album artist, year, genres and `musicbrainzalbumid` from `ProviderIds`, built as an escaped string like every other document in the module.
* `artist.nfo` at the `Music/<AlbumArtist>/` level — `<artist>` with name, biography, genres and `musicbrainzartistid`, from one `api.item(<artist id>)` fetch made only when the file is absent (the same "one series fetch, only when it is absent" rule the show level already follows). The artist id comes off the track's `AlbumArtists`, falling back to `ArtistItems`; a track whose album artist has no Jellyfin entity gets no artist NFO and no fetch.
* `folder.jpg` and `fanart.jpg` at the artist level, from the artist's Primary and Backdrop tags.

`EXPORTED_COMPANIONS` gains `album.nfo` and `artist.nfo` so a directory holding only exported metadata still counts as empty for pruning — the existing rule that the escape hatch must not keep the tree alive. This interacts with D2 and the tests must pin both: an artist directory whose only album is deleted prunes away, and `Music/` does not.

## D6 — one toast per request, and playlist tracks that play

**D6a, the toast.** The store learns what the user actually asked for. `DOWNLOAD_ADD` gains a `Request` field carrying the id of the container the context menu expanded (absent for a single item), `store.Download` gains a `request_id` column, and `_announce_complete` announces on the request rather than the album whenever a request expanded to more than one song. Album and artist downloads are unaffected — their request *is* their album or artist, so the toast reads the same as today — and video keeps its per-item toast for the reason already recorded (a film is the unit somebody chose, and episodes finish minutes apart). `_apply_add` re-arms a request the way it re-arms an album today, so downloading the same playlist twice announces twice.

**D6b, playability.** The `.m3u8` line for a song is decided per row and written by the library poll only (`playlists.playlist_line`): a plugin row keeps its `plugin://` path, a direct row becomes `musicdb://songs/<id><ext>` — and the extension there is load-bearing, because `CMusicDatabaseFile::TranslateUrl` refuses the id when it disagrees with the row. A download repoints the song onto its local file and **nothing tells the playlists**, so every managed line for a downloaded track is stale until the next poll. The leading hypothesis is therefore a transcoded music download changing the container: the line still says `.flac`, the row now says `.m4a`, and the id is refused — which fits all three of the user's observations exactly, since the library row and the Downloads node both reach the song by id and never through that line. S-D6 confirms or kills it before the fix is written, because the three candidate fixes are not interchangeable: re-render the managed playlists after a repoint (local, offline-capable, needs the membership table below), write a line form that survives a container change, or keep repointed rows on their plugin line. The first is the presumptive choice — it is the one that also keeps a *restored* song playable, which has the same bug in reverse.

## D7 — download a playlist from the library, and keep it in sync

A new context item, because the managed `.m3u8` files are plain file rows: `context_playlist.py` declared in `addon.xml` with `<visible>` on `String.Contains(ListItem.FileNameAndPath,/playlists/music/Kofin/)` — matched on the substring rather than a `special://` prefix, since Kodi hands the translated path to that info label. It offers Download / Cancel / Remove and a **Keep in sync** toggle, built from local state the way `_container_download_options` already builds a season's menu.

Mapping the file back to a Jellyfin playlist needs a record kofin does not keep: the managed stem is `_unique_stem(name)` and can be `Name (2)`, so the filename is not the identity. `kofin.db` gains `playlist(jellyfin_id TEXT PRIMARY KEY, name TEXT, stem TEXT, checksum TEXT)` and `playlist_item(playlist_id TEXT, jellyfin_id TEXT, position INTEGER)`, written by the same poll that writes the `.m3u8`. That table is the shared foundation: it is what lets D6b re-render a playlist from MyMusic with no server round trip, what lets this menu name an id, and what lets a subscription diff membership.

The subscription itself reuses the shape `downloadsEpisodeShows` proved: a comma-separated id list in a hidden string setting (`downloadsPlaylists`), a "Manage playlists" action button beside "Manage shows", and a drain on the library poll. Origin is `auto:playlist:<id>` — `store.is_auto_origin` matches on the `auto` prefix already, so the retention rules need no change. Mirror semantics per the decision taken: a track added to a subscribed playlist queues, and a track removed from it has its download removed through the full remove path (never a bare unlink), but only where the row's origin is that subscription — a track the user downloaded by hand and a track that another subscription also wants both stay.

## D8 — download a music library root, and keep it in sync

`actions._expand_downloadable` gains the library-root case: paged `{ParentId: <view id>, IncludeItemTypes: "Audio", Recursive: True}`, the same shape the artist and album cases already use, and `context.DOWNLOADABLE_TYPES`/`DOWNLOAD_CONTAINER_TYPES` gain the type a kofin view row actually carries (`CollectionFolder` or `UserView` — S-D8 reads it off the live row rather than assuming). The confirm dialog needs no change and is the reason this is safe to offer at all: `_confirm_download` already sizes the expansion and refuses what will not fit.

The subscription is D7's, keyed on the library id (`downloadsMusicLibraries`, `auto:musiclibrary:<id>`). One rule carries over from the shows subscription and is load-bearing: a subscription is a standing order and is **exempt from the bulk cap** (`downloadsBulkAlbums`), which exists to stop a server-side bulk import auto-pulling hundreds of albums nobody asked for.

## Order and branches

D4 first, alone, because its answer can move D3. Then `fix/downloads-polish` — D2, D3, D5, D6a, D1 — five independent changes, each with unit tests, none touching the transplant. Then `feat/downloads-subscriptions` — the `playlist`/`playlist_item` tables, D6b, D7, D8 — where the mapping table lands once and three features read it. D1 carries new strings, so it lands with its 28-file translation change (`en_gb` + 26 JSONs + `gen.py --snapshot`, then `gen.py && validate.py && pocheck.py`) and needs a full Kodi restart before it can be seen on the rig.

## Unit tests

`test_downloads_manager.py`: deleting the last movie leaves `Movies/` and removes `Movies/<Title>/`; `_apply_remove_all` leaves the root and no category folder; a twelve-track playlist request announces once and a twelve-track album request still announces once; a request re-queued announces again. `test_clean.py`: `remove_downloads` leaves the root, takes the categories, and still spares a foreign sibling directory. `test_player.py`: an Audio item played past the threshold with a DONE download raises no prompt and notifies nothing, while an Episode in the same state still does. `test_downloads_export.py`: `album.nfo`/`artist.nfo` content and escaping, the artist fetch made once and skipped when the file exists, a track with no album-artist entity writing neither, and pruning still clearing a directory down to its exported companions. `test_downloads_usage.py`: category totals, the `Other` bucket, an unreadable root, and free space unknown rendering as unknown. `test_playlists.py`: the membership table round-trip and a local re-render matching what a full refresh would have written. `test_downloads_store.py`: the `request_id` column and its migration on an existing profile.

## Live verification

All gates on P1D (Debian, native Kodi 21.3 Omega, JSON-RPC over the SSH hop; access confirmed 2026-09-01, kofin 0.22.0 enabled). Mutating work runs on the `kofin-jf12` profile against the local jf12 server, whose libraries are expendable; `kofin-test` is used only where a production-shaped music library is needed, and never for anything that writes to the server. Conventions are `docs/testing-plan.md` §3, and two rig traps apply: `tools/dev-install.sh` never restarts a same-version service, so every deploy is followed by an explicit `Addons.SetAddonEnabled` false→true and a fresh service line in `kodi.log` before anything is asserted; and a new string id needs a full Kodi restart, not a bounce. Deploying this branch means pointing the installer at the worktree — p1d sees it at `/media/minipie/bluecon/dev/plugin.video.kofin/.claude/worktrees/downloads-shakedown`, so `KOFIN_SRC=<that path> tools/dev-install.sh` deploys the branch without disturbing the working tree the other checkout is using. Each gate opens with `kodi-logtail mark` and closes with `kodi-logtail errors`; evidence lands in `tests/live/results/S-D<n>/`.

## Risks

D6b is the only item whose fix is not yet decided, and the gate that decides it runs before the code is written. The `playlist`/`playlist_item` tables are a schema addition to `kofin.db` and need the same migration care as every other one — an existing profile must gain them without a resync. D2's floor change touches the one function three deletion paths share, so its tests carry the whole blast radius. D7 and D8 both queue work from a poll, and a subscription that mirrors can delete files: every removal goes through `_apply_remove` and its repoint/restore refusal, never a bare unlink, and the origin test is what keeps a hand-made download out of a subscription's sweep.
